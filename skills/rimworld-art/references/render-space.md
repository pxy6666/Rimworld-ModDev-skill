# 渲染空间合同

动态视觉任务先把以下三者当作独立维度取证；不能用其中一个维度代替另外两个。

## 1. 坐标轴

逻辑移动、预期屏幕移动和图像 canvas 是三个不同坐标系。对象在地图平面中的起点、终点或轨迹，不自动说明它在屏幕上会向哪个方向移动；PNG 像素位置和 origin 也不等于游戏或 Unity 坐标。记录目标版本、真实消费者、逻辑轨迹、预期屏幕轨迹和素材锚点，不从另一对象机械复制轴映射。

## 2. 渲染图层

render layer 决定对象相对 pawn、身体、apparel、建筑、抛射物或飞行物的前后遮挡，并且可以独立于像素位置和可见位移。同一位置和同一张图使用错误层级时仍会产生错误遮挡。必须按方向和场景取得目标 renderer 的 layer/order 证据。

## 3. 着色器与图形管线

shader/graphic pipeline 决定坐标变化和材质如何被解释成最终画面，例如贴地、飞行、透明叠层或其它渲染方式。相同的坐标移动在不同管线中不保证得到相同视觉结果；必须查明目标版本和真实消费者使用的 graphic class、shader 或框架行为。

## 组合合同

每项飞行、悬浮、projectile、parallax、动画轨迹或图层敏感任务都必须同时描述：

```text
目标位置/轨迹 + 应有遮挡顺序 + 目标渲染方式
```

验收时分别检查三者，再检查组合结果。仅移动坐标、仅换 layer 或仅换 shader 都不能单独证明动态视觉完成。

## 示例：无人机起飞

参考无人机的飞行路线先在 map plane 中移动，再加入朝北的 screen offset，形成可见的升高；flyer 使用较高的 render layer，以获得预期遮挡；flying shader 则让该坐标变化按预期显示为起飞、巡航和下降。

这个无人机案例只是“三者共同构成结果”的证据，不是通用的坐标轴、图层或着色器模板。其它飞行物、悬浮物、抛射物、视差、Apparel 或框架必须重新依据目标版本、相机和真实消费者取证。

## 交接

- `rimworld-art` 定义预期视觉行为、三部分合同、参考素材和预览/验收证据。
- `rimworld-mod` 实现实际 `DrawPos`、Def、render layer、shader 或框架配置变更；本合同不拥有这些绑定。
- 绑定后失败时交给 `rimworld-debug`，附上三部分合同、目标版本、消费者、复现步骤及现有截图/运行证据，以便判断失败来自坐标轴、图层还是着色器。
