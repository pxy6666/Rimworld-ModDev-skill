# Requirement → Plan → Build → Review

所有制作任务先做需求整理与计划检查，再进入实施。这里 Build 指 XML/C#/资源等实际制作，编译只是其检查之一；读取工程、查询接口和检查环境属于前期调查。普通短任务在对话中简要记录即可，复杂任务可在目标工程 `docs/` 或工作记录中保存计划，不要求玩家写规格文档。

## 大循环：整个成品

1. **Requirement**：把口语、零散消息、例子和限制整理成“玩家想得到什么”。记录目标对象、触发/操作、可观察结果、适用版本/工程、必须保留的内容、范围和验收。区分用户已说的事实、代理建议和待选择项；不用含糊的“功能完整/效果好”代替验收。
2. **Plan**：按已确定目标拆功能块，说明连接关系、实施顺序、资源/上游选择和验证方法。标出未确认接口与真正阻塞项。计划检查完成后，才实施相应范围。
3. **Build**：按依赖顺序推进功能块，每块运行下述小循环；已有有效计划和检查可复用。不要在每次进入 XML/C# 分支时重新规划整个 mod。
4. **Review**：用需求和验收逐项对照实际产物、组合行为与证据，区分已满足、失败、未验证、缺资源。遗漏/失败回到相关功能块；需求变化回到 Requirement/Plan。满足约定标准后结束，不无条件迭代或新增功能。

## 需求模糊时先让用户选择

不要按用户消息长短判断明确程度：一句“只把 A 的伤害从 10 改成 12，不加 DLL”也很明确；长篇创意可能仍缺玩法取舍。以下缺口若影响结果，先整理并问：目标对象/玩家行为不明、核心触发或效果有多个合理解释、依赖/成品范围未定、要求冲突、必要资源的正式来源待定。

- 先给一句需求复述，再围绕最多 1–3 个关键决定给易懂选项；每个决定一般 2–3 项，标推荐方案和影响。多轮可以，但不要一次列完整技术问卷。
- 选项描述玩家结果或用户需要承担的代价，例如“命中即恢复固定生命 / 按最终伤害比例恢复”“独立使用 / 依赖已指定框架”。graphicClass、内部类名等通常由代理查证决定，不转嫁给新用户。
- 有可用问答工具时使用；必须由用户决定的选择保持待答。没有工具时在对话里提出并等待。未回复、超时和推荐项预选都不算确认。
- 等待时可读取相关文件、查接口、比较方案、拟计划；不为未选定方案修改实现或先生成其付费资源。已经独立确定的部分可继续必要调查。
- 用户的回答或先前授权已解决选择时沿用，不让用户重复投票；新问题只问新缺口。普通命名、内部拆类、已证实的实现路径可由代理决定。

## 计划审视闸门

实施前让当前计划可见，至少含目标/验收、范围/限制、实施步骤与验证、未决项。小改动可用 2–4 句；多功能 mod 用简短计划和 [feature.md](feature.md) 的连接契约。计划有版本/修订说明时记录选择依据，避免按旧口头需求继续做。

按以下情况判断怎样通过闸门：

| 情况 | 开始 Build 的条件 |
| --- | --- |
| 用户目标与限制明确，计划只是实现已授权内容 | 展示短计划并自检通过，可继续；不固定要求回复“批准” |
| 核心需求模糊或有重大取舍 | 先取得用户选择，再生成/更新计划；检查未决项确已解决后可自检继续 |
| 用户要求“先给计划/看完再做/逐步确认” | 提供具体计划和待决定项，等待明确审视结果后再实施；不能自行把等待改成自检 |
| 用户同意代理决定实现细节 | 在授权内记录合理假设并自检；冲突于明确限制或仍有超出授权的重大取舍时再请求决定 |

自检至少核对：计划覆盖每条需求；没有擅自新增 Def/DLL/依赖/功能；关键接口有依据或调查步骤；资源和连接契约可成立；验证足以观察结果；没有未决问题影响本轮实施。自检不代替未知用户偏好。修正计划可解决的问题先自行修正。

若不能完整审视所有未来功能，可批准已确定的第一块并标出后续未定块；不要把部分计划通过写成整个 mod 已批准。排错/发行中的原工程编译取证不需要伪造新玩法需求，但新增玩法或扩大修复范围时回到制作流程。

## 小循环：一个功能块

1. **Requirement**：从整体计划取出本块目标、输入/边界、验收及对其它块的依赖。
2. **Plan**：查证 Def/配置或事件/服务入口，明确相关 XML/C#/资源端点与最小改动。对计划自检；只在出现新的用户取舍、越过限制或被要求审视时提问。
3. **Build**：制作本块最小完整实现，按需调用 XML、C#、上游和资源分支，运行相关检查/编译。
4. **Review**：对照本块验收检查文件、连接和行为证据；失败只修相关部分并复验。依赖接口变化时更新相关块和整体计划，失效相关验证；不要重新生成全部 XML/C#。

完成各块后回到大循环 Review，检查组合效果、依赖加载、获取/触发路径、资源显示和存档等相关项。未执行游戏测试时留下具体场景与未验证项，不声称全循环已实测通过。

## 示例

明确的小改：“把 A 的伤害改为 12，其它不变。”整理为一个数值目标，展示定位→局部修改→静态/行为检查的短计划，自检范围后执行，最后对照值与证据。

模糊的创意：“做一把厉害的吸血刀。”先整理期望，再问吸血方式、适用对象或成品形态中真正影响玩法的选择；不要自行加入盾、传送、技能树。选定后计划可拆为基础武器、吸血行为、必要显示/资源，各块单独闭环，最后验收它们的组合。
