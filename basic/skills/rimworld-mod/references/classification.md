# 用途、真实类型与运行链

在选模板或写 C# 前读取。六种范围约束允许修改什么；内容/系统/显示描述实现模式；实际类型说明游戏怎样处理本功能。这三者分开判断。

## 从玩家结果反推

每块回答：如何获取/操作？什么触发？谁执行？结果落在哪个对象/输出？谁读取配置？记录最短执行链和可观察验收。用户只需选择影响玩法的解释，不需提供内部类名。

| 玩家目标 | 优先查证的连接，不是固定生成清单 |
| --- | --- |
| 装备后直接远程投射 | 装备/使用入口 → 非近战攻击 Verb/自定义消费者 → 投射物 → 命中结果；核对攻击可用性与显示入口 |
| 近战命中后追加效果/投射 | 近战攻击 → 有效命中事件 → 追加行为/投射 → 输出；填远程词条不等于已连接 |
| 主动施放投掷/能力 | 指令或能力 → 目标选择/消耗/冷却 → 投射/效果；不一定是武器普通攻击 |
| 物品、配方、作物、建筑或 Pawn | 真实用途及配置 → 获取/生产/生长/生成 → 行为与资源；关联 Def 按需存在 |
| 基因、特性、状态、研究等 | 对应 Def/配置 → 赋予或解锁入口 → 消费者 → 玩家效果；定义存在不等于能获取或有作用 |
| 系统/显示功能 | 启动/事件/补丁 → 服务与生命周期 → 状态/筛选 → 输出；不强制新增 Def |
| 上游衍生/兼容 | 提供方 Def、模板、配置类/API → 本方引用/配置/覆写或局部补丁 → 获取/使用结果 |

具体类和字段以目标版本接口为准。同是 ThingDef，类别、行为类、Verb、组件和消费者可不同；同名路径也可能因实际 `Class` 改变语义。XML 根标签可能是自定义 Def 类或抽象模板命名，不能直接当具体类型。

## 判断是否需要自己的 C#

先列逻辑职责，再查原版/已选上游能否通过合法配置提供。已有行为可只写 XML；新事件处理、状态或运算需求才考虑自己逻辑。查看 DLL 不意味着允许新增 DLL。

确需逻辑时记录触发/生命周期、输入、输出、边界、配置读取和持久化。优先合适的组件、worker、虚方法或公开 API，再按实际需要使用 Harmony。XML/C# 两端围绕同一契约连接，不机械先写完 XML 再叠代码。

库型和内容型 mod 都可能提供代码/配置/模板/素材。接口要核对类型、签名、可继承性和调用时机，按 [upstream.md](upstream.md) 记录每条关系。

## 吸血飞刀例

“飞刀”不能自动判近战或远程。先确认直接射出、近战附加投射还是主动技能，再查实际攻击链；吸血另查结算事件、目标、恢复依据和归属。数值按 [contracts.md](contracts.md) 处理。

来自近战物品的父模板不能单独证明投射必然失败；写了射程/精度也不能证明会投射。核对合并攻击配置、自定义行为和使用入口，再验证游戏中触发；不要未经证据把模板标签当错误根因。
