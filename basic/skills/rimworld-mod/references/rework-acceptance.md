# 重做前确认交付与验收边界

替换/重写既有实现、重做界面或系统时读取，包括迁移 B 和迁移 A 中必要的局部重做。普通最小修复沿用既定验收，不为每次修改新增问卷。

先从用户需求和项目记录恢复必须保留的功能、允许改变的体验、已选交付及验证。没有明确依据时，在制作计划前询问“这部分重做到什么状态算完成？”，给相关选项并说明推荐理由：

| 本次交付选择 | 完成边界 |
| --- | --- |
| 原型/技术交付 | 完成约定源码、配置与静态/适用的编译检查，交付具体游戏验证步骤；未实测行为仍标未验证，不能称已可玩或已兼容 |
| 目标功能可用 | 按约定操作实际触发并观察预期，核对首次/重复和相关生命周期；无阻断或关键静默失效，存档/视觉/依赖按涉及范围验证 |
| 可发行交付 | 目标功能可用，再完成约定支持版本/组合、资源许可、干净包和发行说明；只覆盖选定范围，不自动上传或穷尽所有 mod 组合 |

这些选项决定验收到哪里，不决定采用什么实现。迁移 A/B、L1–L6、参数模式仍各自记录；局部重做不自动升级为 B 或全工程重构。用户已有明确选择或委托则直接沿用，不再重复提问；推荐项、未回复和超时不算选择。

## 只问影响结果的缺项

围绕当前内容选 1–3 个关键问题，必要时分轮：

- 哪些原功能/操作必须保留，哪些可以调整？是否接受指定降级或保留项？
- 哪些场景是本次必测：界面开关/输入、进图、重复触发、切图/读档、选定上游消费者或有/无依赖？
- 有改进目标时怎样判定改善：可观察的体验/效果，或性能指标、基线与测试条件？谁提供实际游戏测试和证据？

字段、默认值和接口合法性由代理查证，不变成玩家技术问卷；技术调查可以继续，只暂停依赖未选方案的实现。若用户要求游戏可用但当前无法实测，说明缺口并确认测试分工或明确调整交付，不能代理降到“编译通过就完成”。

将选择写入已有 [功能记录](feature.md)：`重做范围/保留行为 → 本次交付 → 必测动作及预期 → 可接受保留项 → 测试分工 → 确认依据`。先自检可实现性和证据能力，再展示具体计划；验收失败回相关块，标准变化只更新受影响部分。交付报告分别列实际证据、未验证和用户接受项，不能用结束开发代替验收通过。
