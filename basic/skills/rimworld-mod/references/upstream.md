# 上游调用、衍生与修正

每个上游分别记录 packageId、使用版本/程序集、许可依据、引用材料、用法及加载关系，采用工程已有台账。不要为尚未采用的框架预先加硬依赖。

先判断本功能用途与执行链，再找上游提供的具体表面。按 [contracts.md](contracts.md) 优先复用有效记录和 MCP 小查询，必要时只反编译相关类型/方法。把配置字段、合法默认/继承、引用提供方和消费者写入功能契约；上游名称或“lib”标签不能替代接口证据。续作按 [project-state.md](project-state.md) 局部补查，不重新导入全部上游资料。

## 按实际接口选择路径

lib 型和内容型是用途描述，同一 mod 可以同时提供程序集、Def、模板和素材。每个上游按实际公开表面判断，不因它被称为内容 mod 就禁止调用其代码，也不因它被称为库就要求自己的成果必须有 DLL。

| 上游表面与本次目标 | 路径 | 交付 |
| --- | --- | --- |
| 框架提供 XML 配置类，自己的 XML 使用其组件/扩展 | L4，调用或衍生 | 可是完整内容 mod，也可只是适配 XML；无需自己的 DLL |
| 库提供公开方法/可继承类型，自己的代码调用或覆写 | L5，调用或衍生 | 自己的程序集、必要 Def/资源与依赖，或独立代码兼容包 |
| 内容 mod 提供材料/物品/配方/父模板，自己引用它们 | L4，衍生 | 自己的新 Def 与获取/使用入口；核心依赖可为硬依赖 |
| 改上游已有 Def 的数值、列表、组件等 | L4，修正 | 独立 XML patch mod，无需新游戏对象 |
| 改上游已有执行过程或跨 mod 适配 | L5，修正，可同时调用 API | 独立 C# patch mod；按效果查公开入口或 Harmony |
| 直接修复/扩展上游源码仓库 | L6 | 沿用其工程流程；fork 的身份与发布差异按用户目的明确 |

这些路径可组合，完整 mod 按功能块选择。只有公开接口无法满足目标时才考虑内部耦合；数据修正可以直接用 XML 补丁，不需要先证明上游没有公开字段。

## 从依据到交付

1. 确定目标工程与上游的实际版本、启用关系和许可材料；先找到相关表面，避免导入整套框架资料。
2. 为每条连接记录类型/签名、defName/模板、配置字段、生命周期及必要条件。名字存在不等于能合法继承或在这个时机调用。
3. 选硬依赖或可选，记录必要的直接和间接依赖及加载顺序。编译引用 DLL、游戏启用依赖和 XML 引用是三件需一致检查的事。
4. 写自己的最小完整成果；独立 patch 也有自己的 About/身份和必要依赖。自有 Def 与上游引用区分命名，不复制整个上游工程来制造衍生内容。
5. C# 将实际程序集加入目标工程的编译引用。工程采用示例适配器时可用 `config/mod.json` 的 references 与本机 referencePaths；实际是 csproj/多程序集则遵循原生结构，技能包不提供适配器，不强制替换构建。
6. 做范围检查、编译和上游组合验收。硬依赖需测试依赖存在时的功能与缺失时清楚的依赖提示；可选兼容需有/无都能符合约定。框架升级后复核相关接口。

可选 C# 模块若需要隔离多个程序集，采用目标工程能验证的原生构建/条件加载或独立兼容包；当前单程序集 CLI 不自动生成这种架构。

- 调用：用库的公开 API。衍生：自己的内容引用上游 Def、模板、组件。修正：改变上游既有数据/行为。一个功能可以同时包含多种用法。
- 硬依赖与可选兼容按未安装时能否加载并实现主要功能判断；衍生不默认可选。
- 查看公开源码、输入 XML、配置类和实际 DLL；必要时核对运行时 Def。find_usages 无结果不证明不能调用，先确认查询范围、反射和 XML 引用。
- 源码/Def 与运行快照保留版本；上游更新后重新验证受影响接口。私有/internal 不作普通公开 API；反射或补丁访问内部实现应标为耦合。
- 可选 DLL：核心基类、签名、静态初始化中引用外部类型可能在条件判断之前加载失败。选择并验证独立兼容包、条件程序集加载或无需静态依赖的接口方案；上游有/无都测。
- 不猜各条件机制的标识匹配方式，按版本查证。区分游戏 XML 中 Class 的配置类和实例行为类。
- 分开记录许可对读取、复制、修改、再分发的要求；不要把上游 DLL/素材默认打进自己的包。
- 修改上游工程遵循其构建、命名和回归要求；权限范围不因只读分析而扩大。

框架的“库”身份不会把所有补丁任务自动变成非法；任务确实需要修正库行为时按 L5/L6 与依据处理。不要凭规则强行改成调用或放弃任务。
