# 并行分工

制作、排错或迁移包含多个独立任务时，检查当前客户端是否有子 agent 能力，以及用户/工程约定是否允许委派。符合条件且能减少等待或上下文时主动拆分；小改动无须强行并行，没有能力时沿同一清单串行执行。不用创建新聊天代替内部子 agent，不虚构工具。

## 主 agent 先固定

目标版本/画像、范围和限制、已确认计划与制作模式、功能依赖、证据契约、文件归属。用户确认与新取舍统一由主 agent 处理；调查可早于制作，不向子 agent 授权未确认方案。

## 适合并行

- 不同版本或上游的接口取证；各返回精确来源、签名、消费者和缺口。
- 独立功能/素材的已确认制作，前提是文件和生成产物归属不重叠。
- 分离模块的工具修改；稳定接口先约定，再各自实现。
- 独立测试或审查；复杂技能试用提供原始需求和最小资料，不预告期望答案。

各子任务只读必要项目记录，明确允许读写目录、不得做的外部动作与停止条件。返回 `范围/版本/来源 → 产物位置 → 结论与证据 → 未验证/阻塞 → 下一步`，不复制整段源码与全部工具输出。

## 保持顺序

依赖未定的实现、同一文件写入、公共 schema/配置/加载声明和最终合并统一协调；一个文件只设一个写入方。Basic/Image 由唯一源码生成，不让子 agent 手改分发目录。游戏会话和日志不能混用，多版本运行测试分别记录。

主 agent 检查版本、契约和功能组合，解决冲突后运行必要集成验证并保存检查点。子 agent 的“完成”不自动成为游戏验收，也不能自行升迁移深度、删功能、加依赖、改游戏设置或发布。
