# 给原工程增加 1.7 支持

先恢复目标工程、身份、1.6 支持和已确认需求，读 [目标证据契约](../../rimworld-mod/references/version-data.md) 与两版画像。迁移范围与 L1–L6、参数模式、Basic/Image 分开；默认保留原工程和身份，在实际加载约定中增加 `1.7/` 支持，不复制整套项目。

## 目标深度

| 目标 | 路线与完成依据 |
| --- | --- |
| A：在 1.7 能玩 | 主要排错适配。约定核心功能有实际触发证据，无阻断加载/进图、持续错误、关键静默失效或状态破坏；轻微保留项需明确接受，不承诺穷尽所有组合。 |
| B：在 1.7 更好 | 排错已有失败，并逐块评估新接口是否更适合旧职责；确认替换/重做方案后制作。记录具体前后改善和回归，性能收益用测量，UI/维护性可用可检查的定性对照。 |

用户未注明、已有记录也不能明确深度时，在迁移实施前提出 A/B 选择，解释本次影响并给有依据的推荐，不自行默认或把推荐当同意。同时澄清影响方案的制作需求：哪些功能必须保留/允许改变、是否保留1.6、旧档兼容方向、可接受依赖或降级；只问当前真正未定的关键项，可分轮，不要求完整技术问卷。只读调查可继续，已明确选择或委托则沿用。

从 A 升 B、删除/降级功能、新依赖或玩法变化确认变更部分。确需局部或整体重做时，先按 [重做验收](../../rimworld-mod/references/rework-acceptance.md) 询问本次完成边界、必测场景及测试分工，再形成计划；不能只问“是否重做”便开始。图形、UI、lib 等只是功能块，不自动决定深度；已失效机制的旧优化按 [兼容方向](migration-1.7.md) 默认不迁移，其余独立块继续。

## 流程

1. 核对 About/LoadFolders、现有 DLL 与源码可用性、游戏/运行时、实际 Harmony 和上游消费者。区分共享/版本独立/会变化的资源、设置与存档状态。
2. 按实际引用/异常查 [兼容表](migration-1.7.md)，局部比较两版接口和消费者；保存用途、证据、候选和缺口，不重扫全部游戏。库以最小下游用例验证，可选依赖检查有/无。
3. 保存迁移深度、需求选择，以及需要重做块的交付/验收边界和测试分工；自检并展示功能顺序、构建/加载/状态方案、用户/CLI/混合模式和未决项，沿用用户确认后执行。
4. 每个块先 [排错过程](debug-workflow.md)，确需制作/重做进入 [制作过程](../../rimworld-mod/references/production.md)；交接目标、授权、功能记录和待验项，不重新启动整个流程。
5. 对约定功能记录 `触发 → 预期 → 首次/重复/相关生命周期实际结果 → 状态`，组合验收失败回相关块。未游戏触发列未验证并给具体步骤，不写成已兼容。

## 多版本约束

- 游戏 .NET 10 不意味着必须全量 net10.0 重编：按实际依赖选择旧 DLL 验证、原框架重编或新目标重编。无源码不能假装能编译；复杂上游采用自己的原生构建。
- 选定目标的源码、条件符号、框架/引用与产物分别记录，避免递归把两版源码混编。输出隔离，不能覆盖 1.6。共享/根目录及版本目录按实际 LoadFolders 核对，不重复加载 Def 或 DLL。
- 保留旧 DLL 的来源/哈希与游戏证据，和新编译记录分列；包内每个支持版本分别核验，不能拿 1.7 的编译成功覆盖 1.6 的缺证据。
- Scribe 键保留后仍检查类型/枚举/引用、默认值、事件重新订阅与读档恢复。明确支持旧档进入 1.7 还是双向可读，默认不承诺回存；存档副本测试，回退保存原产物和原档。
- 完成对应验收后更新 supportedVersions；版本元数据不是修复。共享状态、加载配置、最终整合由主 agent 协调，独立取证/功能块按 [并行分工](../../rimworld-mod/references/parallel-work.md) 使用子 agent。
