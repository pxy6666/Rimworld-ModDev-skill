# 系统与显示主导功能

对事件、全局服务、面板、覆盖显示或提示型功能使用本分支。它不增加第七种制作深度；成果范围仍为 L3/L5，编辑上游工程时为 L6。

沿用 [workflow.md](workflow.md) 的具体计划确认与制作模式；设置和资源也按 [contracts.md](contracts.md) 查真实消费者/默认后处理未定项。将事件/服务契约与生命周期证据保存到功能记录，不为记录格式强造 Def。

## 查证与连接

1. 明确触发入口、执行时机、对象范围与观察结果；优先已有事件/扩展点，必要时用查证过的 Harmony 入口。不要为流程顺序强加物品 Def。
2. 核对数据的含义和时机：请求伤害不等于实际伤害，护盾损耗不等于身体受伤，未命中与零伤害也可有不同显示语义。
3. 分离入口、数据处理、状态与输出。避免将复杂运算、重复查询和资源创建全部塞进高频补丁或绘制回调。
4. 明确启动注册次数、Map/Game 生命周期、对象销毁/离图、读档和切换地图；有订阅则明确释放。不同 GUI/tick 调用频率不能按每帧恰好调用一次假定。
5. 选择配置与持久化：用户设置、游戏状态、短期缓存和瞬时显示分开。持续设置应验证重启恢复；瞬时浮字不默认写入存档；缓存需要清理/重建策略。

## 显示功能的重点

- 若用户目标仅为信息展示，观测代码应保持结算结果、参数、AI 与游戏状态不变。可视提示允许必要的显示对象，但不要无意写入战斗规则。
- 明确显示条件：目标种类、来源、是否在有效地图、死亡/销毁、不可见区域、屏幕范围，以及开关配置。隐藏信息是否应展示按用户需求定义。
- 检查同一事件的重复入口；身体伤害、护盾吸收、未命中提示各自含义要清楚。避免同一个伤害被多个监听重复显示。
- 验证缩放、暂停/不同游戏速度、密集事件与寿命结束；只在自定义 UI 或实际涉及渲染状态时核对恢复颜色/字体等全局状态。
- 大量触发时关注分配、查询、显示对象数量与限流/聚合需求；依据实测决定方案，不默认建立复杂对象池。
- 多个补丁共存时核对结果是之前还是之后的观察值，不以反编译原方法当作完整运行链。

## 验收顺序

编译与注册 → 单次事件 → 阈值/零值/对象失效 → 配置开关 → 生命周期清理 → 密集事件 → 相关兼容组合。

仅显示功能还要比较开关前后的实际游戏结果。系统功能则验收其约定行为变化。声明支持旧档时验证实际加载；是否保存状态由机制决定，不因没有新增 Def 就免测。
