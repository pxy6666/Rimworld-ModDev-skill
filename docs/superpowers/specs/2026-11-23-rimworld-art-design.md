# RimWorld 单插件与 rimworld-art 设计

## 状态

已通过对话架构评审，等待书面规格审阅。本文只定义目标架构，不实现现有技能迁移。

## 背景

当前仓库把相同的 RimWorld 开发技能复制到 `basic/` 与 `image/`，要求用户先决定是否需要生图，并在同一客户端只启用一版。实际内容差异仅涉及少量图像路由文本和一份图像管线说明，其余制作、排错、迁移、发行技能重复。

这种结构有三个问题：

1. 安装时的 Basic/Image 选择与具体任务无关，增加了入口负担。
2. 生图能力藏在 `rimworld-mod` 的引用文件中，无法作为独立技能稳定发现。
3. Apparel 生成没有把“匹配 pawn/body 身型基准并叠合校准”变成强制流程，生成出的服装可能尺寸、方向或位置错位。

## 目标

- 只发布一个 `rimworld-moddev` 插件。
- 保留现有 RimWorld 1.6、1.7、制作、排错、迁移、发行与发布入口。
- 增加可独立发现和调用的 `rimworld-art` 技能。
- 明确 `rimworld-mod`、`rimworld-art` 与 `rimworld-debug` 的职责边界。
- 为 apparel 建立强制的身型对位、叠合核验和文件坐标保持流程。
- 区分 RimWorld/Unity 的平面位置、视觉位移、渲染层排序与着色器行为。
- 支持现有图标、物件、建筑、UI、贴格和效果素材，不把所有任务都路由到生图。

## 非目标

- 不内置或托管图像生成服务。
- 不在没有真实图像工具时声称已生成素材。
- 不自动发起付费、切换模型或静默替换用户已选来源。
- 不让 `rimworld-art` 修改与美术无关的玩法数值、C# 逻辑或 XML 行为。
- 不把生图能力拆成第二个插件，也不长期维护 Basic/Image 镜像。
- 不默认复制原版或上游身型素材进发行包；其正常用途仅是对位参考。

## 方案比较

### 方案 A：继续保留 Basic/Image

只把图像说明拆成独立技能，但仍复制整套插件。

- 优点：兼容当前市场结构，迁移最小。
- 缺点：双份代码与文档继续漂移，用户仍需选择插件。
- 结论：不采用。

### 方案 B：基础插件加可选图像插件

基础开发能力与图像能力分别安装。

- 优点：功能边界清楚。
- 缺点：用户需安装两个插件，并处理依赖、版本同步和重复入口。
- 结论：不采用。

### 方案 C：单插件内包含独立 rimworld-art

市场只安装一个插件，插件内部按任务路由到独立图像技能。

- 优点：安装一次；技能仍具备清晰边界；不依赖平台生图能力也能使用其他功能。
- 缺点：一次性重构目录和市场文档。
- 结论：采用。

## 目标架构

### 插件分发

仓库市场只发布一个条目：

```text
rimworld-moddev
└── skills/
    ├── rimworld-16-mod
    ├── rimworld-16-debug
    ├── rimworld-17-mod
    ├── rimworld-17-debug
    ├── rimworld-17-migrate
    ├── rimworld-help
    ├── rimworld-setup
    ├── rimworld-mod
    ├── rimworld-debug
    ├── rimworld-art
    ├── rimworld-release
    └── rimworld-publish
```

现有 1.6/1.7 入口继续处理版本特定制作与排错，不形成两个插件分发版本。五个平台的插件清单、市场清单、README 与手动安装说明统一指向该单一插件。

### 入口与路由

- `rimworld-help`：首次使用和目标分类。用户要画图、改图、批量换款、apparel 或统一风格时转入 `rimworld-art`。
- `rimworld-mod`：负责玩法和内容契约，包括资源用途、真实消费者、Def/C# 绑定、加载根和技术规格。
- `rimworld-art`：负责外观方向、参考图、生成/编辑、资源批次、apparel 对位、文件检查、视觉对照和游戏视觉验收记录。
- `rimworld-debug`：处理已绑定资源仍出现的错位、缺图、渲染错误、方向错误或运行时显示异常。
- `rimworld-setup`：仅探测当前会话是否有真实图像工具；工具不可用不阻止 XML/C# 工作。
- `rimworld-release`：只检查已接受资源、来源条件、发行清单和视觉验收记录，不在打包阶段补做未完成美术。

技能之间通过资源契约交接：

```text
用途 / 消费者 / 目标版本 / 路径 / 体型 / 方向 / 图形类 /
drawSize / 层级 / shader / 保留项 / 来源授权 / 验收状态
```

`rimworld-art` 不拥有 Def 绑定逻辑；`rimworld-mod` 不重复图像来源、样稿审批和 apparel 对位流程。

### rimworld-art 文档结构

```text
rimworld-art/
├── SKILL.md
└── references/
    ├── apparel-alignment.md
    ├── render-space.md
    ├── image-sources.md
    ├── gfx-batch.md
    └── visual-acceptance.md
```

- `SKILL.md`：分类任务、检查工具与授权、选择普通素材或 apparel 流程、定义交接和停止条件。
- `apparel-alignment.md`：强制的身型基准、合成模板、坐标保持和多方向/多体型验收。
- `render-space.md`：Unity/RimWorld 三轴、`AltitudeLayer`、视觉偏移、着色器和动画轨迹契约。
- `image-sources.md`：builtin、connector、CLI/API、用户提供和手工来源；不保存密钥。
- `gfx-batch.md`：样稿、批量重绘、朝向、状态、贴格和共享风格管理。
- `visual-acceptance.md`：文件、alpha、小图可读性、绑定、同步、游戏显示和未验证状态。

## 渲染坐标、图层与着色器

RimWorld 基于 Unity 渲染，但视觉结果不能只从 PNG 或三维坐标猜测。`rimworld-art` 将视觉问题拆成三个独立维度，先分别确定，再联合验收。

### 1. 坐标轴：对象在哪里移动、视觉上应往哪里画

先区分逻辑位置、视觉位置和图片自身坐标。某条轴控制地图平面运动，不代表它同时负责屏幕上的“升高”；某条轴用于渲染排序，也不代表移动该轴一定会产生可见位移。具体映射随目标版本、相机和图形管线查证，不能机械照搬其他 mod。

技能需要记录“逻辑起点/终点是什么、屏幕上应怎样运动、素材 canvas 如何对齐”，并避免把游戏坐标、Unity 坐标和 PNG 像素坐标混为一谈。

### 2. 图层：谁应显示在谁前面

遮挡顺序是渲染层级问题，不能只靠移动或裁切图片解决。需要确认对象相对 pawn、身体、apparel、建筑、抛射物、飞行物等应使用的排序层或框架层级，并分别检查不同方向的遮挡。

同一张画得很准的 PNG，如果图层错误，仍会出现在身体后、外衣下或天空物体前。Apparel 的 South/North 前后关系、动态对象穿过建筑时的遮挡，都属于这一维度。

### 3. 着色器：坐标如何被解释成最终画面

着色器和图形类决定素材以贴地、飞行、透明叠层还是其它方式渲染。相同坐标变化在不同着色器下可能没有相同的屏幕效果，因此必须按目标版本查明所用管线，不能只凭更改图片或坐标自信完成。

### 三者组合

视觉任务的最小契约是：

```text
目标位置/轨迹 + 应有遮挡顺序 + 目标渲染方式
```

`rimworld-art` 负责描述和预览这三者的预期结果，`rimworld-mod` 负责把实际位置、图层设置、Def、着色器或框架配置落到目标版本。若结果不对，先定位是哪一维失败，再决定改素材、图层还是渲染实现，不能直接重复生成图片。

### 参考例：无人机起飞与飞行

- 飞行路线在地图平面上运行，并额外使用朝北的平面偏移制造屏幕上的“升空”效果。
- 无人机被放到合适的高空排序层，使其与地面内容保持预期遮挡关系。
- 使用飞行类着色器后，坐标变化才按预期成为可见的起飞、巡航和下降；仅修改某个坐标轴不会自动产生完整飞行效果。

这个例子用于说明“三者必须一起工作”，不作为所有飞行物、服装或特效的固定模板。具体轴、层和着色器仍需对目标版本和真实消费者取证。

## Apparel 专项流程

普通图标、建筑或独立物件不得被误套用此流程。若资源是 `Apparel`、穿戴层、身体覆盖层、头饰/发型配套或任何依赖 pawn 身型锚点的素材，则必须走 apparel 对位。

### 1. 确认真实消费者

根据目标游戏版本和实际工程确认：

- Apparel Def、继承链、`wornGraphicPath` 或框架等价配置。
- 图形类、层级、`drawSize`、shader、遮挡和方向命名。
- 实际支持的性别、身型、年龄或种族变体。
- 方向、状态、损坏态和动画是否分别需要素材。
- 贴图通过哪个 LoadFolders 根实际加载。

这些信息由 `rimworld-mod` 提供或由 `rimworld-art` 只读查证，不能从常见习惯猜测。

### 2. 获取身型基准

从实际目标身型对应的原版或上游素材中找到基准身体，优先使用运行时已安装且版本匹配的资源；必要时也可使用用户授权的工程素材。

基准必须与以下约束匹配：

- 目标体型或 apparel 预期消费者。
- 同一方向约定。
- 原始画布尺寸与像素坐标系。
- 真实透明背景。
- 来源及使用条件已记录。

基准主要用于对位和验证，不自动进入发行目录。若发行依赖运行时资源，也要单独记录依赖与合法引用，而不是把“参考”误写成可发行素材。

### 3. 建立拼合模板

为每个实际消费者生成固定画布模板。模板至少包含：

- 身型基准层。
- 透明 apparel 层。
- 方向与体型标识。
- 固定原点、画布边界与允许绘制区域。
- 所有需要保持的身体锚点，如肩线、腰线、手臂、腿部和足部位置。

生成或编辑时直接在模板上工作；禁止只生成一张孤立服装图后猜测其在角色上的位置。对于多体型或多方向，应分别使用对应模板，不把不同体型缩放到同一张图后假定可用。

### 4. 生成 apparel 层

生成工具看到的输入必须包含身型基准和 apparel 保持区域。提示中明确：

- 只修改 apparel，不重画身体。
- 保持模板画布、位置、方向和透明区。
- 参考风格只影响服装材质和线稿，不改变锚点。
- 不新增未经授权的角色、装备、背景、文字或额外身体部位。

工具返回结果若混入身体、棋盘背景或其它不可分离元素，先正确处理或重新生成；不得把身型底图作为正式 apparel 文件导入。

### 5. 保持文件坐标

导出正式 apparel 层时必须遵守：

- 保留基准模板的原始 canvas 尺寸。
- 不自动 trim、crop、recenter、旋转或统一缩放。
- 不因透明边界改变图像原点。
- 保留真实 alpha，不保留预览棋盘。
- 文件名、方向后缀和目录映射与消费者严格对应。
- 多体型/多方向逐一落地，不把单方向结果复制冒充全部方向。
- 最终像素不携带图层排序职责；South/North 等遮挡关系仍由渲染层契约控制。

任何必须缩放或裁切的后处理都要先说明原因，并重新进行叠合检查。

### 6. 叠合检查

正式导入前，对每个 body/sex/type/direction 组合生成“身型 + apparel”叠合预览，并至少检查：

- 头部、肩部、胸腰、手臂、腿部和足部是否对位。
- 服装是否错位、悬空、陷入身体或覆盖错误层。
- 左右方向是否镜像错误或锚点漂移。
- South/North 的人体遮挡、apparel 前后层级以及 Pack/Belt 模式是否与消费者相符。
- 透明边缘、留白和小图辨识度是否正常。
- 同一动作或状态下各方向是否保持一致。

只看 apparel 单图、只检查 PNG 能打开、或只确认尺寸数字相同，都不构成通过。叠合预览必须与导出的实际文件使用同一 canvas 和坐标。

### 7. 绑定与游戏验收

只有叠合检查通过后才把文件交回 `rimworld-mod` 绑定路径。绑定后分别记录：

- 文件已生成。
- 容器、尺寸、alpha 和坐标已检查。
- 叠合预览通过。
- 工程路径/Def 已绑定。
- 本机或测试目录已同步。
- 游戏内静止、移动、不同方向和相关装备状态已验证。

没有游戏证据时准确标为待实测，不能把静态叠合通过写成“游戏内显示正确”。

### 8. Apparel 失败与回退

出现以下情况时，不进入正式批量：

- 找不到版本、体型或方向匹配的身型基准。
- 生成工具不支持参考图、编辑或可分离图层。
- 输出无法保留 canvas、alpha 或原点。
- apparel 与身型无法可靠分层。
- 某个体型/方向叠合失败。
- South/North 或相邻外衣的图层顺序无法在目标渲染器中得到明确证据。
- 原版/上游参考的使用条件未确认。

可允许返回人工素材、用户提供图层、原型占位或更窄的交付范围；不能用随机生成或孤立 PNG 冒充已完成 apparel。

## 普通图像流程

非 apparel 资源保留轻量流程：

1. 从真实消费者确定用途、规格、方向和路径。
2. 明确来源与授权，锁定风格、保留项和样稿。
3. 先做代表样稿，再扩展相关款式。
4. 处理真实 alpha、透明边缘和棋盘背景。
5. 保持文件、路径和引用一致。
6. 核对小图辨识度、方向、拼接或消费者映射。
7. 区分工程绑定、本机同步和游戏视觉证据。

`rimworld-art` 不因为一张图由 AI 生成就要求额外工具；用户已有合格素材时走编辑、复用或直接导入路径。

## 来源与安全边界

`rimworld-art` 只使用当前任务实际授权的来源：

- `auto`：检查当前能力并请求可用来源，不自动发起 API。
- `builtin`：使用会话实际提供的图像工具。
- `connector`：使用已连接且能返回真实图像文件的工具。
- `imagegen-cli`：仅在用户明确选择 CLI/API 且连接能力真实可用时使用。
- `manual`：使用用户交付的文件，未交付时保持待生成。

配置只保存来源名称、连接器或工具名、可选模型和环境变量名，不保存密钥。来源失败时保留真实原因，不静默切换来源、模型、分辨率或付费级别。

## 迁移与兼容

实施时将 `basic/` 和 `image/` 的公共内容合并为单份技能树；当前两版真正不同的路由、来源检查和 GFX 说明迁入 `rimworld-art`。

下一主版本市场中只保留 `rimworld-moddev`。README 说明：

1. 删除或禁用旧的 `rimworld-moddev-basic` 或 `rimworld-moddev-image`。
2. 安装统一 `rimworld-moddev`。
3. 使用原有制作、排错、迁移、发行入口；图像任务改用 `rimworld-art`。

为避免长期保留冗余，不设置 Basic/Image 永久别名插件。若实施阶段发现某客户端必须靠旧 ID 升级，则只作为短期兼容发布项处理，并在同次变更中定义明确移除版本。

## 验证要求

实现后至少验证：

### 结构

- 五个平台市场/插件清单只暴露统一插件。
- 技能数量、名称与 `catalog.json` 一致。
- `rimworld-art` 可被客户端独立发现。
- Basic/Image 的旧目录不再包含第二份公共技能树。
- 所有 README 安装命令指向统一插件。

### 路由

- 纯 XML/C# 任务不会被要求生图。
- “生成/编辑贴图”和“统一风格”进入 `rimworld-art`。
- “apparel/服装/穿戴贴图”进入 apparel 专项流程。
- 已绑定后显示错位进入 `rimworld-debug`，并携带基准、消费者、叠合证据和复现步骤。

### Apparel

- 用测试夹具覆盖至少一个多方向 apparel。
- 覆盖至少一个需要身型基准的素材。
- 验证 trim、crop 或 recenter 不破坏原 canvas 原点。
- 验证叠合预览引用的是正式导出的同一文件，而不是另一份预览专用图。
- 验证参考身型素材不会被错误打入发行清单。

### 回归

- 现有 1.6/1.7 入口仍能找到正确公共流程。
- 迁移、调试、release 与 publish 文档中的相对路径全部有效。
- 技能目录不存在指向已删除 Basic/Image 路径的链接。
- 图像工具不可用时，非图像任务仍可继续，图像任务准确报告待生成而非冒充完成。

### 渲染空间

- 测试夹具明确区分逻辑平面 x/z、渲染排序 y/altitude 和 PNG 坐标。
- 飞行或悬浮任务验证：只改 y 不被当作可见升空；需要时同时有 x/z 视觉偏移、正确排序层和着色器。
- 动态对象跨过 pawn、建筑和其它图层时核对实际遮挡顺序。
- 在目标版本中验证 apparel 的 South/North 层级，而不把层序问题误判为 PNG 锚点问题。
- 运行时图层、着色器与视觉证据关联到具体版本；从其它版本或其它框架复制结论时重新查证。

## 完成定义

单插件安装、独立 `rimworld-art`、普通图像流程、apparel 身型对位、渲染坐标/图层/着色器契约、五平台清单、README 和技能相对引用全部一致。用户不再需要选择 Basic/Image，图像工具是否存在不影响非美术技能的使用；apparel 任务若缺少可用身型基准或叠合验证，动态视觉任务若未区分平面位移、排序层和着色器，则不能被标记为完成。
